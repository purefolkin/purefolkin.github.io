# Neclues — Purefolk Control

Development foundation for the Neclues admin interface.

## Current state

- Development-only branch: `build/neclues-foundation`
- `index.html` is a responsive navigation shell for the Purefolk admin domains.
- The shell is not connected to Supabase, authentication, or website publishing.
- No production schema, data, settings, or live website files have been changed by this work.

## Architecture boundary: Product domain

This implementation must preserve the existing Purefolk product architecture decisions.

### Existing database facts

The current `public.pf_products` table includes:

| Field | Current type / meaning |
|---|---|
| `id` | UUID, generated by `gen_random_uuid()`; primary key |
| `name` | Text |
| `description` | Nullable text |
| `category` | Text; default `food` |
| `price` | Integer |
| `original_price` | Nullable integer |
| `image_path` | Nullable text |
| `image_alt` | Nullable text |
| `tally_param` | Nullable text |
| `is_available` | Boolean; default true |
| `is_jain` | Boolean; default true |
| `is_satvik` | Boolean; default true |
| `is_high_protein` | Boolean; default false |
| `sort_order` | Integer; default 0 |
| `created_at` | Timestamp with time zone |

The database schema is a fact about the current implementation, not proof that every field is correct for the final model. A boolean such as `is_available` cannot represent the complete product lifecycle and publication model.

### Locked conceptual decisions

- Product ID is a permanent system identity and is not the SKU.
- Product name is customer-facing and can change without creating a new Product ID.
- Historical orders must preserve the product name, price and configuration purchased at the time.
- Product Type, Customer Category, Attributes, Collections / Customer Intent, and Search / Discoverability are separate concepts.
- Attributes such as High Protein, Jain, Satvik and Vegetarian do not automatically become product categories or separate products.
- Product lifecycle, website visibility, availability, and ordering state are separate dimensions.
- Published slugs are controlled; a name change must not silently change a published URL.
- Avoid hard deletion of business-critical records; use archive, deactivation, versioning and audit history where appropriate.

### Open decision

Variant / sellable configuration remains **OPEN**. Do not silently decide how regular/large, SKU, price, recipe mapping or order line items relate. Resolve the model against the existing architecture workbook before migration.

## Implementation sequence

1. Build the admin interface and navigation in this development branch.
2. Map approved product fields to existing schema, marking existing vs target vs open.
3. Review authentication, authorization, RLS policies and audit requirements.
4. Design additive database migrations and compatibility behavior.
5. Connect product reads in development and verify output.
6. Implement controlled writes only after validation and authorization checks.
7. Connect website publication through an explicit publishability gate.
8. Test regression and security before any production release.

## Safety rule

Do not publish this page to production or add live data mutations until authentication, authorization, data contracts, lifecycle rules, and publication safeguards have been verified.
